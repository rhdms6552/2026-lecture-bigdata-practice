## Task 1
Bloom filter는 삽입한 비트를 지우지 않고 같은 위치를 조회하므로 false negative가 없다. 예상 오탐률 0.860%와 실측 0.840%의 작은 차이는 유한한 조회 표본의 변동으로 설명할 수 있다.
FM은 해시 64개를 8개씩 묶어 기하평균 후 중앙값을 사용해 24,196개(실제 19,953개, 1.21배)를 얻었다. 같은 레지스터의 단순 평균은 46,208개, 중앙값은 16,384개여서 큰 추정값의 영향과 결합 방식의 차이를 확인했다.
Reservoir는 i+1번째 항목마다 randrange(i+1)로 j를 뽑아 j<k일 때만 교체하므로, 전체 길이를 몰라도 각 항목의 최종 선택 확률이 k/n이고 저장량은 k개다.

## Task 2
i7-1260P·RAM 약 16 GB에서 n=6,400,000의 정확한 set 계산이 36.23초로 30초를 넘어 반복 실험에서는 시간부터 부담스러워졌다. Chrome·Codex가 열려 있었으며 메모리 고갈로 중단한 것은 아니다.
n을 64배 늘렸을 때 set 피크는 4.02→197.49 MiB(49.08배, 대략 선형), FM은 14,630→14,640 bytes(1.00배, 거의 일정)였다. 메모리는 tracemalloc 추가 할당 피크이며 전체 RSS가 아니다.
FM의 추정/실제 비율은 1.06~1.64배로 정확한 개수를 보장하지 않는다. 방문자 규모를 대략 파악하는 데는 2배 오차가 쓸모 있을 수 있지만, 사용자 수에 따른 요금 청구나 정산에는 부족하다.

## Task 3
p=(1-exp(-kn/m))^k를 최소화하면 k=(m/n)ln 2이므로 10 bits/item에서 6.93에 가까운 7개 해시를 골랐다. 이론 최저 오탐률은 exp(-10(ln 2)^2)=0.8193%다.
실측 오탐률은 1,719/200,000=0.8595%, false negative는 0개였다. 객체·배열 헤더·시드를 포함한 보관 메모리는 80,000비트이고 실제 필터 비트 79,160개 기준 예측 0.8622%에 가깝다.
n을 작게 예상하면 포화로 오탐이 늘고, 크게 예상해 공간을 잡으면 메모리를 낭비한다. n이 미지수라면 필터 층을 추가하되 메모리도 늘려야 하며, 고정 예산으로 무한한 전체 이력과 낮은 오탐률을 동시에 유지할 수는 없다.
