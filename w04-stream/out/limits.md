# Week 4: 정확한 집합과 Flajolet-Martin의 메모리 비교

## 측정 환경과 방법

측정일: 2026-09-28. CPU: 12th Gen Intel(R) Core(TM) i7-1260P. RAM: 16,787,636,224 bytes (15.63 GiB, 약 16 GB). 운영체제: Windows-10-10.0.26200-SP0; Python 3.11.8. 실행 중 확인한 앱: chrome, codex. 백그라운드 부하와 CPU 클럭을 통제한 실험은 아니다.

제공된 생성기를 그대로 사용했다. seed=246, 가능한 키 범위는 n×0.4이며 반복을 허용해 n개를 생성한다. 따라서 실제 distinct 수는 n×0.4보다 작고, 표의 정답은 정확한 set으로 직접 센 값이다. FM도 같은 seed와 n으로 스트림을 다시 생성해서 읽었다. 입력 전체를 리스트로 만들지 않았으며 각 방법은 생성기를 한 번만 순회한다.

시간은 `perf_counter`, 메모리는 `tracemalloc`로 측정했다. 두 방법 모두 스트림 생성과 알고리즘 실행을 포함하며 메모리 추적을 켠 상태의 wall time이다. 메모리 피크는 추적 시작 후의 Python 할당량이며 전체 프로세스 RSS나 OS 메모리가 아니다. FM은 해시 64개를 고정해서 사용했다. `bench.py`, `test_tasks.py`, 루트 `check.py`는 수정하지 않았다.

```text
cd w04-stream
python task2_limits.py --sizes 100000,400000,1600000,6400000
```

실제 실행은 중단에 대비해 크기별 결과를 저장하며 이어서 진행했다. 표에는 최종 알고리즘의 완료된 실행만 담았다. 더 큰 크기를 추가한 경우 아래 표와 `limits.json`에 기록된다.

## A2: 멈춘 기준

이번 실험에서는 정확한 계산 한 번에 30초 이상 기다리는 것을 반복 실험에 부담스러운 지점으로 삼았다. 처음 이 기준을 넘은 표본은 n=6,400,000이며 set에 36.23초가 걸렸다. 이 크기까지 실제로 실행한 뒤 증량을 멈췄다. 시간부터 부담스러워진 것이고, RAM 고갈이나 MemoryError를 경험했다고 주장하지 않는다.

FM도 반드시 빠른 방법은 아니다. 64개 해시를 처리하고 Python에서 메모리를 추적하는 비용이 있으므로, 표의 속도와 공간 절감을 구분해야 한다. 이 실험에서 핵심 이점은 제한된 메모리로 개수를 추정한다는 점이다.

## A4: 두 메모리 증가율

n이 64배 커질 때 set 피크는 4,219,244→207,086,882 bytes로 49.08배 증가했다. 두 끝점으로 계산한 지수 log(M₂/M₁)/log(n₂/n₁)는 0.936로, 대략 선형 O(distinct) 증가와 맞는다. 집합의 해시 테이블은 일정 크기마다 재할당되므로 모든 구간이 정확히 같은 비율로 늘지는 않는다.

FM 피크는 14,630→14,640 bytes로 1.001배, 같은 방식의 지수는 0.000이다. 해시 수 64개와 64비트 해시 폭이 고정이므로 저장하는 레지스터·마스크·현재 digest 크기가 n과 함께 늘지 않는다. 작은 측정 차이는 키 문자열 길이와 일시 할당 등에서 생길 수 있으며 입력을 누적 저장한 결과가 아니다.

## A5: 정확도와 활용 범위

예를 들어 오늘 방문자가 대략 수만 명인지 수백만 명인지 파악하는 운영 대시보드에는 2배 수준의 허용 오차가 쓸모 있을 수 있다. 반대로 고유 사용자당 비용 청구, 정산, 계약상 정확한 수치에는 적합하지 않다. 이 실험의 허용 범위는 모든 입력에 대한 정확도 보장이 아니다.

## Task 1: 같은 레지스터의 결합 방식 비교

교수님 검증과 동일하게 seed=246으로 120,000개를 생성했다. 실제 distinct는 19,953개다. SHAKE 출력의 서로 다른 64비트 구간을 64개 해시로 사용하고, 각 해시에서 뒤에 붙은 0의 개수 R의 최댓값을 저장했다. 다음 수치는 같은 레지스터에 결합 방식만 달리 적용한 결과다.

| 결합 방식 | 추정 | 실제 대비 |
|---|---:|---:|
| 2^R의 산술평균 | 46,208 | 2.316× |
| 2^R의 중앙값 | 16,384 | 0.821× |
| 8개씩 산술평균 후 중앙값 | 41,216 | 2.066× |
| 8개씩 중앙값 후 산술평균 | 32,256 | 1.617× |
| 8개씩 기하평균 후 중앙값 (선택) | 24,196 | 1.213× |

선택한 방식은 각 그룹에서 R을 평균한 뒤 그룹 평균들의 중앙값에 2를 거듭제곱한다. 즉 `2 ** median(mean(R_group))`이다. 큰 2^R 한 개가 산술평균을 지배하는 영향을 줄이면서 단일 중앙값의 거친 단계도 완화한다. 보정 계수를 정답에 맞추어 끼워 넣지는 않았다.

| 해시 seed | 선택한 추정/실제 |
|---:|---:|
| 246 | 1.213× |
| 0 | 1.322× |
| 1 | 1.112× |
| 2 | 0.935× |
| 3 | 1.791× |
| 4 | 1.506× |

각 seed에서 동일한 데이터를 새 생성기로 읽었으며 위 6개 시험은 모두 0.5~2배 안이었다. 이것이 모든 해시·모든 데이터에 대한 보장은 아니다. 빈 스트림은 0을 반환하고, 중복 항목은 같은 해시값을 내므로 새로운 최댓값을 만들지 않는다.

계산 최적화는 64개 구간을 큰 정수로 묶어 개선 가능한 레지스터가 있는지 먼저 검사하는 것이다. 가능성이 없을 때만 개별 구간 순회를 건너뛰며, 간단한 전체 순회 구현과 모든 레지스터가 일치하는지를 `test_extra.py`에서 검증했다. 저장하는 입력 항목 수는 늘어나지 않는다.

Bloom filter는 비트를 켜기만 하고 지우지 않으며 조회도 같은 해시 위치를 확인하므로 넣은 항목에 대한 false negative가 없다. 예상 오탐률 `(1-exp(-kn/m))^k`는 0.8605%, 20,000개 미삽입 조회의 실측값은 0.8400%였다. 차이 0.0205%p는 유한 표본 변동 범위다. Reservoir는 i+1번째 항목에서 `randrange(i+1)`로 j를 뽑아 j<k일 때만 교체한다. 기존 항목의 생존확률과 새 항목의 진입확률이 모두 최종 k/n이 되며 전체 길이를 미리 몰라도 된다.

## Task 3: 이론 최적값과 실제 메모리

오탐률 p(k)=(1-exp(-kn/m))^k에서 log p를 k로 미분해 0으로 놓으면 exp(-kn/m)=1/2이고, k*=(m/n)ln 2이다. m/n=10이면 k*=6.931이므로 정수 7을 선택했다. 최적 연속값의 오탐률은 exp(-10(ln 2)^2)=0.819255%, k=7일 때는 0.819372%다.

미삽입 조회 200,000개 중 1,719개가 오탐으로 0.8595%였고 false negative는 0개였다. 이상적인 10 bits/item의 이론값과 차이는 0.0402%p이며, 0.9% 이하 조건을 만족했다.

`memory_bits()`는 필터 인스턴스 40 bytes와 유일하게 소유하는 bytearray의 실제 할당 9,960 bytes를 더해 80,000 bits를 보고한다. bytearray에는 시드 8 bytes도 포함된다. 헤더와 시드를 제외한 실제 필터 비트는 79,160개라 예측 오탐률은 0.8622%이며 측정값에 가깝다. 입력을 숨겨서 저장하는 집합·목록·캐시는 없고 크기도 삽입에 따라 늘지 않는다.

여기서 예산은 필터가 소유하여 보관하는 상태 전체를 뜻한다. 공통 Python 실행기·클래스 코드·호출 스택과 해시 계산 중의 일시 작업 공간은 필터의 보관 상태에 포함하지 않는다. 전체 프로세스 메모리가 10 KB라는 주장은 아니다.

제공된 NaiveFilter는 bytearray(n_bits)를 쓰므로 bytearray만 80,057 bytes를 할당하지만 memory_bits()는 논리 비트 수 80,000을 보고한다. 공식 harness와 baseline은 그대로 유지했고, 제출한 YourFilter는 실제 압축 비트 배열과 객체 오버헤드를 포함해 80,000비트 안에 맞췄다.

n이 예상보다 크면 비트가 포화되어 오탐률이 올라가고, 필요 이상으로 큰 n에 맞춰 공간을 잡으면 메모리가 낭비된다. n이 미지수라면 목표 오탐률별로 Bloom filter 층을 추가하는 방법을 고려할 수 있지만 추가 메모리가 필요하다. 고정 메모리에서 무한히 커지는 전체 이력에 낮은 오탐률을 영구 유지할 수는 없다. 오래된 층을 지우려면 조회 대상도 최근 시간 구간으로 명시적으로 바꿔야 한다.
